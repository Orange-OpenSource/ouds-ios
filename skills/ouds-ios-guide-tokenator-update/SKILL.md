# Skill: ouds-ios-guide-tokenator-update

Load `ouds-ios-guide-vocabulary` first if you are not familiar with tokenator, providers or token layers.

This skill is for agents (GitHub Copilot as pull request reviewer, or a local agent) checking an update made by the tokenator.
The tokenator can produce defects. Every anomaly found is called **suspect**.

## 1. Output rule (mandatory)

Every suspect element MUST be clearly displayed in the logs / review output, one line each:

```
⚠️ SUSPECT [CODE] <file>:<line> — <short description>
```

At the end, print a summary: the count per code, or `✅ No suspect element found`.
In a pull request review, each line becomes a review comment on the matching file and line.
Do NOT silently fix anything: report first, propose a fix, let the human decide.

## 2. Scope

- Providers (implementations): `OUDS/Core/Themes/<Theme>/Sources/Values/{SemanticTokens,ComponentTokens}/`
- Protocols and raw tokens: `OUDS/Core/Tokens/*/Sources/Values/`
- Changed files only: `git diff --name-only <base>...HEAD`

Matching is case-insensitive and "contains", not exact (use `rg -i`).

## 3. Checks

### 3.1 `FIGMA_TEST_TEXT` — leftover test text
The text `// Test for support Figma.` must not be present.
```
rg -in "test for support figma" OUDS/
```

### 3.2 `ELEVATION_SPREAD` — spread in elevation tokens
Elevation tokens must not mention the notion of `spread` (names, doc comments, values, protocols or providers).
```
rg -in "spread" $(git ls-files | rg -i "elevation")
```

### 3.3 `WRONG_VISIBILITY_DOC` — wrong visibility in documentation
A token documented as internal / not public whereas its declaration is `public` or `open` is suspect.
Look at the `///` comments just above any `public` / `open` declaration for: `internal`, `not public`, `non-public`, `private`.
```
rg -in -B3 "^\s*(@objc )?(public|open) " <changed files> | rg -i "internal|not public|non-public|private"
```

### 3.4 `TOKEN_NOT_IN_PROTOCOL` — token missing in the protocol
Each token (`var`) added in a provider implementation (`extension <Theme>…Provider: <X>Tokens`) must be declared in the associated protocol.
1. List `var` names added in the diff of provider files.
2. Search each name in the matching protocol file (`*SemanticTokens.swift`, `*ComponentTokens.swift`).
3. Missing → suspect.

### 3.5 `DEPRECATED_NOT_MARKED` — deprecated token without Swift attribute
A token considered deprecated (under `// MARK: - Deprecated (since …)`, or documented `Use instead`, or with `TODO: vX - Remove this old token`) must be marked in the **protocol** with the Swift keyword:
```swift
@available(*, deprecated, message: "Use xxx instead")
```
Absent attribute in the protocol → suspect.

### 3.6 `MANUAL_ADDITION_REMOVED` — manual additions deleted
Manual additions in provider implementations must survive a regeneration. Lines like these must NOT be removed:
- `// MARK: - Deprecated (since tokens library vX.X)`
- `// TODO: vX - Remove this old token`
- `/// Use instead xxx`
- `// [File not generated by the tokenator]` and related WARNING comments

Check the diff for deleted lines:
```
git diff <base>...HEAD -- OUDS/Core/Themes OUDS/Core/Tokens | rg -i "^-.*(MARK: - Deprecated|TODO: v[0-9]+ - Remove|Use instead|not generated by the tokenator)"
```
Any match → suspect (also report deprecated tokens fully deleted whereas not scheduled for removal).

### 3.7 `HEADER_VERSION_OUTDATED` — tokens version header
Generated files have a header:
```
// 🧬 Tokens version: 2.8.0 (Orange brand)
// 🤖 Generated by Tokenator
```
The version must be updated in every regenerated file and equal the target version.
- Target version: read the **commit message** (title and body, e.g. `integration of tokens library v1.6.0`) with `git log <base>..HEAD --format=%B`.
- Check all headers:
```
rg -n "Tokens version:" OUDS/Core/Themes | rg -v "<target version>"
```
Any header with another version in a file touched by the update → suspect.
Also read the commit message body for warnings (e.g. "some tokens have been manually updated"): these manual changes must be kept and are not suspect.

## 4. Procedure

1. Get the target version and warnings from the commit messages.
2. List changed files.
3. Run checks 3.1 to 3.7.
4. Print every `⚠️ SUSPECT` line, then the summary.
5. Propose fixes without applying them, unless the user explicitly asks.

## 5. Known false positives

- Files tagged `[File not generated by the tokenator]` are hand-written: no header version expected.
- Deprecated tokens kept on purpose are valid if they are marked deprecated in the protocol.
- Words like `private` in unrelated comments: confirm by reading the declaration context.
